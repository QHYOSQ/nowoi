FIELD GUIDE 02 / 使用体验

让表单错误告诉人下一步

从一封发不出去的咨询邮件出发，把标签、原生校验、错误说明与恢复路径放在同一条流程里。

一个小型工作室只需要回复潜在客户的咨询。访客认真写了项目背景，提交后却看到一句“发生错误”。他不知道是地址写错、说明太短，还是网络出了问题。表单校验的任务，是保住这份已经付出的努力，并给出一个能完成的下一步。

读完，你会得到

  • 先用可见标签与原生约束说明要求，再为具体错误补充修正路径。
  • 通过 aria-describedby 关联提示，修正后清除旧错误并保留输入。
  • 本地校验不能证明邮箱归属，也不能代替服务器校验或发送确认。
01

01 / 先写下表单真正需要什么

这个练习需要两个字段：用于回复的邮箱，以及项目说明。邮箱必填；说明至少十个字符，最多一千个字符。这只是本例的业务约定，不是所有网站都应照搬的标准。用一行提示提前解释长度和用途，比等用户提交后才公布规则更公平。

给每个控件一个可见的 label，并用 for 对上输入框的 id。占位文字会在输入后消失，不能承担字段名称。邮箱使用 type="email"、autocomplete="email" 和 required；说明使用原生的 minlength 与 maxlength 表达约束。

<label for="email">回复邮箱</label>
<input id="email" name="email" type="email"
  autocomplete="email" required
  aria-describedby="email-hint email-error">
<p id="email-hint">我们用它回复这次咨询。</p>
<p id="email-error"></p>

这里先不要求手机号、预算和公司名称。每增加一个必填项，都应该能说明它如何影响这次回复。

02

02 / 别让“格式不对”包办一切

空邮箱的错误是“请填写用于回复的邮箱”；填写 maya@ 后，应提示“请检查邮箱地址，例如 name@example.com”。不要使用“非法输入”这样的责备口吻，也不要把示例当成唯一允许的格式。

借助输入框的 validity.valueMissing 与 validity.typeMismatch 区分原因。不要叠加一个只允许英文字母、只允许某个后缀或拒绝加号的简陋正则。maya+notes@example.com 是值得保留的测试输入；语法看上去合理，并不证明这个地址存在、能收信或归访客所有。

检查说明长度时，把下一步写明白：“请至少写十个字符，说明你想制作什么。”保留已经填写的内容。若暂时不能完成网络请求，应说“暂时未发送，请稍后重试”，不要把连接失败标在邮箱旁边，让人徒劳地修改地址。

03

03 / 让提示与输入框建立关系

第一次打开页面时，空字段不是需要立刻批评的错误。提交后检查必要字段，在有问题的控件旁显示文字，并把 aria-invalid 设为 true。修正成功后，移除无效状态和旧错误，但保留正常的帮助说明。

aria-describedby 可以同时引用提示与错误元素；对应的 id 必须真实存在且保持唯一。这样输入框获得焦点时，辅助技术才有机会读到相关说明。红边可以帮助定位，文字负责解释原因；不要只依赖颜色或一个无名的感叹号。

两个字段出错时，在表单开头提供简短摘要，并把焦点送到第一个无效字段，或采用可聚焦且包含字段链接的摘要模式。选定一种一致的方式，避免多个实时区域与焦点移动同时抢着播报。若使用 setCustomValidity()，问题修复后必须传入空字符串清除错误，否则浏览器会继续阻止提交。

04

04 / 试验一次完整的修正过程

  1. 不填写任何内容，直接提交。应能知道哪些字段缺失，并立即找到第一个问题。
  2. 邮箱输入 maya@，说明写“我想做网站”。再次提交，观察邮箱错误与说明长度提示是否各自准确。
  3. 将邮箱改成 maya+notes@example.com，说明改成一段超过十个字符的完整需求。错误应消失，之前的内容不应被清空。
  4. 只用键盘完成同一过程。标签、帮助文字和错误之间的关系，不应该依赖鼠标悬停才能发现。

本页的表单实验用于观察校验反馈，不会真的发送咨询。实验里的完成状态，只说明样本符合本地规则。生产表单只有在服务器确认接收后，才能告诉用户“已发送”；点击按钮本身不构成成功。

还要故意制造一次失败：断开网络或模拟服务器拒绝，然后确认用户可以保留内容并重试。这个恢复路径经常比漂亮的成功动画更有价值。

05

05 / 浏览器校验之外，还要做什么

原生约束让常见错误更容易被发现，但客户端规则可以被绕过。服务器仍要独立检查字段是否必填、类型与长度是否符合约定，并处理请求频率、滥用和存储安全。别把“按钮已经禁用”当成服务端保护。

若业务需要确认邮箱归属，应设计确认邮件，而不是编写越来越长的正则。国际化地址、输入法和不同浏览器的表现，也需要按目标用户单独验证。本例没有承诺识别所有真实邮箱，更没有验证可投递性。

上线前再读一遍每条提示：它是否指出具体问题，说明一种修正方法，并让人继续完成原来的任务？能回答这三个问题的错误说明，才真正减少了提交阻力。

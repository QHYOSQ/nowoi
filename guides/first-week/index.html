FIELD GUIDE 06 / 发布与维护

网站发布后的第一周

把上线当作观察的起点：先确认访问与操作真实可用，再让反馈决定下一次修改。

一个小型资料站终于有了正式网址。首页可以打开，并不代表从旧书签进入、用键盘切换语言、在手机上完成练习也都正常。发布后的第一周适合建立一条短而可靠的维护路径：记录实际现象，保留复现步骤，修改后回到同一条路径核对。以下七天是可调整的工作安排，不是搜索收录、流量增长或广告审核的承诺。

读完，你会得到

  • 在正式域名直接检查页面、旧地址和不存在的地址。
  • 用键盘和手机完成实际任务，并记录检查条件。
  • 搜索验证与收录状态都不等于 AdSense 批准。
  • 维护记录应区分已核对、待查和无法复现。
01

01 / 宣布上线之前，留一份访问基线

先列出首页、一篇教程、一个练习、联系页和一个确定不存在的地址。直接输入这些网址，不要全部通过首页点击进入。这样能发现静态部署的深层路径、刷新以及错误页配置问题。

例如旧文章 /notes/image-size.html 已永久迁到 /zh/guides/image-budget/，就应将它重定向到相关新内容，而不是统一塞回首页。永久迁移通常使用 301 或 308；具体规则要在实际托管平台验证。完全不存在的路径应返回真正的 404，而不是只画一个“找不到”界面却返回成功状态。

访问样本期待结果核对证据
正式教程地址200，正文与标题正确页面和文档请求状态
有对应新内容的旧地址永久重定向，最终到达相关页面重定向链和最终地址
随机不存在的地址404，有可用返回入口HTTP 状态与错误页内容

在生产地址上检查，而不只在本地预览。记录日期、网址、浏览器和结果；不要把一份尚未执行的检查表标成全部通过。浏览器网络面板中的文档请求，可以帮助确认服务器真正返回了什么。

02

02 / 第一天，完整完成一件事

选择一个真实目标，例如“找到图片预算教程，调整练习里的数字，再返回目录”。先把鼠标放到一边，仅用键盘完成。用 Tab 和 Shift+Tab 移动，核对焦点是否看得见、顺序是否合理，链接和按钮能否按预期激活。若有弹层，检查能否关闭，以及关闭后焦点回到哪里。

再用手机走同一条路径，检查菜单、表格、代码和结果区。没有实体设备时可以先用窄屏模拟，但要把它记录成模拟检查。以约 360 个 CSS 像素宽度和浏览器放大后的阅读状态作探查，观察是否出现被遮住的按钮或必须左右拖动才能读完的普通段落。

清楚、与内容吻合的页面标题也属于这条路径：打开两个教程标签，看看读者能否分辨。修正“能点但不知道发生了什么”的反馈，比添加装饰更直接。一次键盘和手机检查只是基础筛查，不能据此宣称已经通过全面无障碍审计。

03

03 / 第二至三天，检查搜索看到的版本

在 Search Console 验证正确的网站资源后，挑选几个有代表性的完整网址进行网址检查。已编入索引的数据与实时测试回答不同问题：前者展示 Google 已知的版本，后者帮助检查当前页面是否可能被抓取和索引。实时测试成功，不等于页面已经进入索引。

核对抓取到的正文、资源加载和页面状态；如果提交站点地图，地图里的地址应是希望公开、可正常访问的正式地址。只有检查发现了异常，才去修改对应的重定向、robots 或 noindex 配置，不要见到“尚未收录”就盲目解除所有限制。

Google 明确说明，返回 200 也不保证收录。提交索引请求同样不是立即收录的保证；对于刚上线的网站，先保留观察记录。Search Console 负责搜索可见性，AdSense 有独立的站点与政策审核，因此“已验证”“已收录”都不能作为广告批准的承诺。

04

04 / 第三至五天，收集能复现的反馈

比“网站不好用”更有帮助的反馈是：“在某个页面，想完成什么，做到哪一步，预期和实际有什么差别。”提供联系入口，并邀请用户描述这些内容。不要要求提交正在处理的真实文件，尤其是合同、账号信息或其他私密材料；可以请对方用合成样本复现。

先处理阻止任务完成的问题。例如“按下导出没有反应”通常比“卡片间距希望更大”更紧急。但应先复现：确认是否仅在某个浏览器、隐私设置或特定输入下出现。保存最小样本、操作顺序和可见错误，避免仅凭一条模糊反馈重写整站。

若没有收到反馈，就实际执行前一天的访问路径，或邀请愿意参与的人测试。不要编造用户评价、使用人数和成功率来填补空白。没有数据也是当前状态的一部分，应该如实记录。

05

05 / 第六至七天，写下能追溯的维护记录

每个重要修改保留四项：发现的问题、受影响的路径、采取的修改以及修改后的核对结果。下面是一条格式示例，不是本站已经发生的测试记录：

问题：手机菜单关闭后，键盘焦点丢失。路径：教程页 → 打开菜单 → 关闭。修改：关闭后将焦点还给菜单按钮。核对：在指定浏览器重复该路径；其他浏览器待查。

“已修复”应对应已重复的步骤。仍未核对的环境写成待查；无法复现则写明尝试条件，不必强行给出结论。发布一项修改后，顺便检查相关路径：菜单改动可能影响所有页面，单个例子的修订则未必需要全站重测。

将尚未完成的问题按影响排序，选择下一周能完成的小批次。维护记录可以公开说明有价值的变化，但不应暴露用户输入、私人邮箱或内部错误信息中的凭证。

06

06 / 留下一条可以重复的维护循环

下方发布检查练习适合记录自己的待办与复核结果。它是一份辅助清单，不能自动访问你的网站、替你检查服务器，也不会向 Google 提交任何申请。只有实际完成相应检查，再把项目标为完成。

第一周结束时，目标是一组可信的事实：哪些网址正常，哪个操作受阻，哪条反馈已处理，哪些问题仍待查。不要用“所有指标全绿”代替这些事实，也不要为了申请广告临时堆砌与读者目标无关的文章。

之后每次增加教程、依赖或功能，都重复“访问、操作、观察、修改、复核”这条循环。对于小站，稳定地把一个问题解决清楚，往往比一次铺开很多未经验证的新页面更容易维护。

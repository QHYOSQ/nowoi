FIELD GUIDE 04 / 构建基础

图片预算，先于压缩

先决定一张图为什么存在、显示多大、何时需要，再决定把质量滑块拉到哪里。

设想一个介绍社区工作坊的页面：顶部是一张活动照片，下面有两张材料示意图。设计稿很好看，手机上却要等图片加载，文字还会突然往下跳。直接把三张图全部“再压一点”可能损失细节，却没有解决尺寸、加载顺序和预留空间的问题。先给图片分配任务与预算，修改才有方向。下文数字均为教学假设，不是 NOWOI 或某个网站的测速成绩。

读完，你会得到

  • 先确认用途与显示尺寸，再分配图片预算。
  • 传输文件与解码后的像素数据不能混为一谈。
  • 预留比例、准确的响应式候选和合适的加载顺序需要分别处理。
  • 预算计算用于比较假设，实际体验需要在浏览器中验证。
01

01 / 每张图先领一个任务

把图片放进页面之前，写出一句理由：这张图帮助读者做什么决定？活动照片让人了解现场环境，材料图帮助辨认要携带的工具，纯装饰背景可能没有必要。预算从删除不需要的请求开始，而不是从选择文件格式开始。

再记录每张图的最大显示宽度、宽高比和出现位置。假设正文最多宽 680 个 CSS 像素，手机两侧各留 16 像素。照片适合 3:2，示意图里的小字则需要在实际显示尺寸下检查。不要为了得到同一个压缩百分比，给所有图片套同一套尺寸与质量。

为信息图补充相邻的文字说明。即使图像没有加载，读者仍应能理解材料清单；替代文本则简洁描述图片在当前上下文中的作用。图片存在的理由越清楚，越容易决定哪些细节值得保留。

02

02 / 原文件、传输量、解码内存是三件事

相机导出的 3.2 MB 原图是制作素材，不必直接发送给访客。假设你另存一张 1440 × 960 像素、110 kB 的网页版本，110 kB 是编码文件大小；实际网络传输还会受到缓存、响应头等因素影响，应在浏览器里查看。这里的 kB 按十进制计算，1 kB 为 1000 字节。

看什么这个假设例子用于什么判断
制作原件3.2 MB留作以后重新裁切与导出
网页编码文件110 kB规划下载成本，再以实际请求核对
像素数据估算1440 × 960 × 4 字节，约 5.27 MiB理解小文件也可能需要较多解码内存

最后一行只是假定每像素四字节 RGBA 的粗略模型，既不是浏览器进程的实测占用，也不包含全部缓存和渲染开销。图像格式、颜色表示与浏览器实现都会影响实际情况。把质量从 80 调到 70 可以减小文件，却不会自动减少像素数量；尺寸过大时，先裁切和缩放往往更有针对性。

03

03 / 图片没到，位置先留好

页面开始排版时若不知道图片高度，图片出现后就可能把正在阅读的文字挤下去。这是布局偏移的一种来源。给图片写上准确的 width 与 height，浏览器就能提前推导比例；响应式样式可用 max-width: 100%; height: auto; 让它随容器缩小。

例如 1440 × 960 的照片在 600 像素宽的容器里应占 400 像素高。它并不需要固定显示成 1440 像素宽。若设计采用裁切容器，则应明确容器的 aspect-ratio，再确认裁切不会丢掉重要人物或信息。

核对所有候选图的比例是否一致。若手机端换成另一种裁切，就分别考虑对应比例；填一个与文件不符的高度，仍可能在图片出现时纠正布局。预留空间能解决这一类问题，不能保证整个页面的 CLS 一定达标。

04

04 / 把选择交给浏览器，但把条件写准确

srcset 列出实际存在的候选文件及其像素宽度，sizes 描述图片在不同视口下预计占用的显示宽度。它们不会替你生成文件，也不会改变页面布局。下面的文件名只是示例，必须先导出对应图片再使用。

<img
  src="workshop-960.webp"
  srcset="workshop-480.webp 480w,
          workshop-960.webp 960w,
          workshop-1440.webp 1440w"
  sizes="(max-width: 720px) calc(100vw - 32px), 680px"
  width="1440" height="960"
  alt="工作坊的长桌旁放着剪刀与彩纸"
  fetchpriority="high">

例子假设页面样式确实在窄屏留出共 32 像素边距，宽屏图片显示为 680 像素。若实际布局是双栏卡片，就要重新写条件。浏览器会综合显示宽度、设备像素比等条件选择资源，并不是永远下载最小文件。在开发工具中查看实际请求，再用不同视口和像素比复查。

05

05 / 首屏重要图片不要一律延迟加载

位于页面顶部的大图可能成为最大内容绘制，即 LCP 的候选元素。若给它添加 loading="lazy"，就可能额外推迟加载开始。将关键图片直接放在初始 HTML 中，不对它使用懒加载；示例里的 fetchpriority="high" 只是优先级提示，应留给确实重要的图片，而非全站图片。

较远的正文插图可以考虑懒加载，同时继续保留尺寸。不要仅凭图片位于源码第一行，就认定它一定是 LCP：在另一种视口里，标题文字也可能成为最大元素。用性能记录识别实际元素及等待发生在哪一步，再调整策略。

只有把资源压小，并不能消除服务器响应慢、资源发现过晚或渲染阻塞造成的延迟。应针对观察到的瓶颈修改，避免把“加载更积极”误写成“加载一定更快”。

06

06 / 预算是可检验的假设

给这个示例页面暂定 300 kB 的初次资源预算：首图 110 kB，两张插图各 35 kB，其余 HTML、样式和脚本合计 120 kB。总数为 300 kB。再假设可用吞吐量为每秒 200 kB，仅把这些字节传完的算术结果是 1.5 秒。

1.5 秒不是页面加载时间，也不是 LCP 预测。这个除法没有模拟连接建立、延迟、请求调度、缓存、解码或渲染。用下方预算练习调整假设，目的是看懂资源之间的取舍，而不是获得测速分数。

  1. 导出候选图，并在最终显示尺寸下检查文字、边缘和颜色。
  2. 打开浏览器网络面板，分别观察首次加载与缓存后加载，记录选中的文件。
  3. 改变视口，观察图片出现前后是否挤动正文。
  4. 记录性能检查的设备、网络条件与时间，修改后在相同条件下比较。

如果预算不够，先问某张图能否删去、缩小或推迟，而不是无限降低质量。保留原件和导出参数，下次更换设计时就不必从已经模糊的网页文件继续压缩。

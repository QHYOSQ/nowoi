FIELD GUIDE 02 / User experience

Write form errors people can fix

Connect labels, native constraints, and specific feedback so a failed submission becomes a recoverable step.

NOWOI / FIELD NOTES8 min readFirst edition 2026.11.08

Try it in the workshop ↗

A visitor writes a careful project inquiry to a small studio, presses Send, and receives “Something went wrong.” They cannot tell whether the address, the message, or the connection caused it. Useful validation preserves that effort and gives them one practical way forward.

What you will take away

  • Use visible labels and native constraints, then explain the specific repair.
  • Associate help and errors, clear stale invalid states, and preserve input.
  • Local validation cannot establish email ownership or replace server checks.
01

01 / Define the actual task

This exercise needs a reply email and a project description. Require an email; ask for a description between ten and one thousand characters. Those limits are decisions for this example, not universal rules. Explain the requirements before submission, including why you need the address.

Give each control a visible label whose for matches its id. A placeholder disappears during typing and cannot replace that label. Use type="email", autocomplete="email", and required for the address. Express message limits with native length attributes.

<label for="email">Reply email</label>
<input id="email" name="email" type="email"
  autocomplete="email" required
  aria-describedby="email-hint email-error">
<p id="email-hint">We use this to reply to your inquiry.</p>
<p id="email-error"></p>

Leave phone numbers and company details optional unless this workflow genuinely needs them. Every required field should have a reason beyond filling a layout.

02

02 / Separate different failures

An empty address needs “Enter an email address for our reply.” An entry such as maya@ needs “Check the email address, for example name@example.com.” The example illustrates a format; it is not the only permitted pattern.

Distinguish missing input with validity.valueMissing and a syntax mismatch with validity.typeMismatch. Avoid adding a simplistic expression that bans plus signs, unfamiliar domain endings, or legitimate punctuation. Keep maya+notes@example.com among your fixtures. Plausible syntax does not establish that an address exists, receives mail, or belongs to this visitor.

For a short description, state an action: “Write at least ten characters describing what you want to build.” Keep the text already entered. A failed network request needs a retry message, not an email error that sends someone into unnecessary editing.

03

03 / Connect feedback to its control

A fresh, empty form should not immediately criticize the visitor. After submission, show text beside invalid controls and set aria-invalid="true". Once the problem is corrected, remove the invalid state and old error while retaining ordinary help text.

aria-describedby can reference both help and error elements. Their IDs must exist and remain unique. This association lets assistive technology provide relevant context when the input receives focus. A colored border can aid location; words explain the problem. Do not rely on red alone.

For multiple failures, add a short summary and focus the first invalid field, or use a focusable summary with links to the fields. Choose a consistent approach rather than several competing announcements. If you use setCustomValidity(), clear it with an empty string after correction; an old custom message otherwise continues blocking submission.

04

04 / Rehearse the entire repair path

  1. Submit with both fields empty. Check that you can identify each missing value and reach the first problem immediately.
  2. Enter maya@ and a description shorter than ten characters. Submit again and check that each message explains its own field.
  3. Change the address to maya+notes@example.com and write a complete, longer request. Old errors should clear without erasing either value.
  4. Repeat with only a keyboard. Finding instructions must not depend on hovering a pointer.

The form lab demonstrates local feedback; it does not send an inquiry. Its completion state means the sample satisfies local rules. A production form may claim delivery only after its server confirms acceptance, not merely because a button was pressed.

Also simulate a failed request and verify that the visitor can retry with the original message intact. Recovery matters as much as a polished success state.

05

05 / Keep the server boundary clear

Native constraints catch common mistakes, but client-side rules can be bypassed. A receiving server still needs its own required-field, type, and length checks, plus suitable abuse controls and safe storage. A disabled button is not a server-side safeguard.

If the workflow requires address ownership, use a confirmation process rather than an increasingly ambitious regular expression. Internationalized addresses, input methods, and browser differences need checks against your actual audience. This example does not promise universal address recognition or verify deliverability.

Before release, read every error aloud. Does it identify a specific problem, offer a correction, and let the person continue their original task? Those three properties turn validation from a rejection into useful assistance.

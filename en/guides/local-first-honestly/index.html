FIELD GUIDE 05 / User experience

What “local processing” can honestly promise

Separate tool inputs, browser storage, page visits, and third-party requests before writing a privacy claim.

Someone wants to tidy an unpublished meeting note. “Processed in your browser” sounds reassuring, but it does not answer three separate questions: is the text uploaded, is a draft saved, and does visiting the site create logs? Trust depends on matching the actual data path to the promise. This guide describes a design and verification method, not a certification of every tool labeled local.

What you will take away

  • Tool inputs, page requests, and external services follow different paths.
  • Persistent browser storage needs a purpose, an explicit choice, and deletion controls.
  • Inspect requests and storage with synthetic samples and record the limits.
  • Recheck privacy statements when dependencies or behavior change.
01

01 / Draw the boundary first

Follow one action: paste MEETING-DEMO-47, transform it, and export the result. List the input, output, storage, and requests separately. Browsers can read user-selected files and calculate locally; that capability alone does not establish that a particular implementation avoids uploads.

DataPossible destinationQuestion to answer
Text or selected filesPage memory, or a server if transmittedDoes the tool upload this content?
Drafts and preferencesBrowser storageWhat saves them, and how are they removed?
Page requestsHosting or CDN infrastructureWhat do the actual logging settings retain?
Fonts, analytics, adsExternal servicesWhich services receive what?

“Tool inputs are not uploaded” is a specific boundary. It does not mean that fetching the website produces no network traffic or that visitors are completely anonymous.

02

02 / Make processing and saving separate choices

For a temporary text utility, a clear design is to process input in page memory without silently persisting it. This is a product decision to implement, not protection the browser automatically supplies.

localStorage belongs to an origin and can persist across sessions without automatic expiry. It is not an encrypted vault; scripts running on that origin can access it. Saved content may also be visible to the next person using a shared browser.

If drafts are necessary, provide an initially unchecked “Save drafts in this browser” option. Explain the contents, location, and deletion method. Write only after the user opts in and saves. Report storage failures honestly: browser policies, quotas, or private browsing can affect availability.

03

03 / Follow a harmless sample all the way through

Use a distinctive synthetic string such as MEETING-DEMO-47. Open the network panel before reloading so initial and later requests are captured. Note domains, request types, and initiators; then transform, copy, export, and save the sample.

  1. Inspect new requests, including Fetch/XHR, form submissions, analytics, and error reports.
  2. Look for the sample in request URLs, query parameters, and visible request bodies.
  3. Compare browser storage keys and values before and after each action.
  4. Refresh and check whether restoration matches the explanation.

Keep sensitive content out of URLs, where it may enter history, logs, or shared links. This inspection covers the current version, environment, and tested actions. Absence of the sample is not proof about every path, future update, or browser extension. Review code and repeat checks after changes.

04

04 / Name exactly what export and deletion affect

An export lets the user choose where a result lives. Avoid inserting sensitive document titles into filenames. Explain that clearing the page does not remove files already downloaded, text copied elsewhere, or backups.

Distinguish “Clear current input” from “Delete this browser's draft.” The latter must remove the tool's stored data as well as reset its interface. This illustrative line removes one named key:

localStorage.removeItem("example-tool:draft");

Do not casually use localStorage.clear(), which could remove unrelated preferences on the same origin. Refresh after deletion to check restoration. Open exported files to verify characters and line breaks. Where temporary object URLs are used, release unneeded references at the appropriate point in the download implementation.

05

05 / Write a promise that can be checked

A useful statement might read:

This tool transforms text in your browser without sending that text to our servers. Draft saving is off by default. A draft remains in this browser only after you enable saving and save it. Hosting and enabled external services handle page requests as described in the privacy notice.

This is example wording to verify against the implementation. It is unsuitable for a tool that calls a remote model or API. Separately document external fonts, ads, analytics, and error monitoring. Check that input or output is not accidentally included in events or error messages.

No registration, local computation, and no saved drafts describe different things. Confirm hosting log retention from actual configuration or provider documentation rather than inventing an immediate-deletion claim.

06

06 / Recheck whenever the boundary changes

Adding analytics, advertising, feedback, or remote error reporting can change the data path. Record the service, transmitted data, trigger, and corresponding notice update in the release log.

Use the data exercise to distinguish processing, storage, and requests. Draft a promise, then find implementation evidence for each sentence. Narrow claims that cannot be connected to code, configuration, or a repeatable check.

Consider whether a web tool suits especially sensitive material before using it. Do not request real contracts, credentials, or medical notes merely to demonstrate local behavior. Synthetic samples can verify most formatting and storage workflows without making the check itself another disclosure.

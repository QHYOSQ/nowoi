FIELD GUIDE 03 / User experience

Finish a page using only a keyboard

Choose native controls, keep focus visible, and give every interaction a predictable entrance and exit.

NOWOI / FIELD NOTES9 min readFirst edition 2026.11.08

In this walkthrough

Try it in the workshop ↗

Your studio page has navigation, filters, an inquiry form, and a confirmation dialog. Everything works with a pointer, but focus disappears when a visitor tabs toward a filter card. Start with the route someone needs to finish, then choose the controls that make that route dependable.

What you will take away

  • Use links for navigation and native buttons for actions; avoid positive tabindex.
  • Keep focus visible, persistent, and clear of clipping or fixed content.
  • Check dialog entry, exit, and focus return within a complete task route.
01

01 / Separate navigation from actions

Use a link with a real href to navigate to another page or location. Use a button to open filters, clear input, or show a dialog. Inside a form, give ordinary action buttons type="button" so they do not accidentally submit it. Reserve type="submit" for submission.

<a href="/en/guides/readable-data/">Read the data guide</a>
<button type="button">Open filters</button>

Native controls bring established roles, focus behavior, and activation keys. Links typically activate with Enter; buttons support Enter and Space. A clickable div, even with a button role, does not inherit the complete behavior. Avoid nesting buttons inside clickable card links. Give navigation and local actions distinct, understandable targets.

02

02 / Follow the logic of the document

Arrange a sensible document order before styling the layout. If Tab jumps unpredictably across a visually orderly grid, inspect its structure and visual reordering. Positive tabindex values make selected controls jump the queue and become difficult to maintain. Ordinary explanatory paragraphs do not all need tab stops.

Reload and put the pointer aside. The first Tab should ideally reveal a way to skip repeated navigation. Continue through navigation, primary actions, form controls, and the footer. The route should match the task, with no hidden interactive stops.

Open the launch checklist on this page. Tab to an item, use Space to change it, and move backward with Shift + Tab. Focus should remain somewhere predictable after the change. Completing a checklist is practice, not evidence that an entire site meets an accessibility standard.

03

03 / Keep the current target visible

At every step, someone should be able to see where their next keypress will act. Preserve the browser's focus outline or provide a clear replacement. Hover styling is insufficient, and an active navigation marker does not identify keyboard focus.

a:focus-visible,
button:focus-visible,
input:focus-visible,
textarea:focus-visible {
  outline: 3px solid #126b52;
  outline-offset: 4px;
}

This is a starting style, not a compliance certificate. Inspect it against light, dark, and image backgrounds. Check that containers do not clip the outline and fixed navigation does not cover a focused input. A mobile keyboard may also obscure the field being edited.

Do not fade the indicator after a few seconds or move focus to the top when an animation finishes. The visible location must continue to match the visitor's actual interaction.

04

04 / Give dialogs a return route

If the project genuinely needs a modal dialog, consider native dialog with showModal(). Adding a dialog role alone does not make the background inert or manage focus. Provide a clear title, a visible close control, and an Escape exit.

Place initial focus somewhere appropriate: often a safe cancel action for a short confirmation, or a heading or introductory text for longer content. While the modal is open, Tab and Shift + Tab should remain within it, and background controls should be unavailable.

let returnTo;
openButton.addEventListener('click', () => {
  returnTo = openButton;
  dialog.showModal();
});
dialog.addEventListener('close', () => {
  if (returnTo?.isConnected) returnTo.focus();
});

Native dialogs already provide some focus restoration; this snippet makes the intended destination explicit. Usually return to the opener. If it was removed, choose a logical next task location. Do not create a keyboard trap in an ordinary, non-modal section.

05

05 / Leave a repeatable acceptance route

  1. Reload, then traverse the main page forward and backward. Record invisible focus or unexpected ordering.
  2. Activate links with Enter and buttons or checkboxes with Space. Check for unintended scrolling and duplicate submissions.
  3. Complete a form, trigger an error, repair it, and continue. Focus must support that correction.
  4. If a modal exists, open it, traverse both directions, close with Escape, and verify the return target.
  5. Repeat in a narrow window and at an enlarged zoom level. Look for obscured controls and clipped outlines.

Describe failures as a page, control, keypress, and observed result. That is actionable; “keyboard support is bad” is not. Keyboard checks do not replace screen-reader, touch, or other assistive-technology checks. They establish one concrete task route you can repeat after the interface changes.

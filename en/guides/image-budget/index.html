FIELD GUIDE 04 / Build the basics

An image budget comes before compression

Decide why an image exists, how large it appears, and when it is needed before moving the quality slider.

NOWOI / FIELD NOTES8 min readFirst edition 2026.11.08

In this walkthrough

Try it in the workshop ↗

Imagine a community workshop page with a large photograph and two material diagrams. On a phone, the images arrive slowly and push the description downward. Compressing everything harder may remove useful detail without fixing dimensions or loading order. Assign each image a job and an allowance first. All numbers here are teaching assumptions, not measurements of NOWOI or another website.

What you will take away

  • Decide purpose and display dimensions before assigning bytes.
  • Encoded downloads and decoded pixel data are different quantities.
  • Space reservation, responsive sources, and request timing solve different problems.
  • A budget compares assumptions; browser checks reveal actual behavior.
01

01 / Give every image a job

Write what each image helps a visitor decide. A workshop photograph shows the setting; a diagram identifies supplies; a decorative texture might be unnecessary. Removing an unhelpful request is a better starting point than choosing its compression format.

Record the maximum displayed width, aspect ratio, and position. Suppose the article is at most 680 CSS pixels wide, with 16-pixel margins on narrow screens. The photograph suits a 3:2 crop, while labels in a diagram need inspection at their final display size. These assets should not automatically share one quality setting.

Keep the supply list in nearby text, so it remains understandable when the diagram is unavailable. Alternative text should describe the image's purpose in this context.

02

02 / Separate three kinds of size

A 3.2 MB camera original is an editing asset. Suppose its web derivative is 1440 by 960 pixels and 110 kB. That encoded file size helps plan downloads; actual transferred bytes depend on factors including caching and response overhead. Here, kB means 1000 bytes.

QuantityAssumed exampleUseful for
Editing original3.2 MBFuture crops and exports
Encoded web image110 kBA download allowance to verify
Pixel-data estimate1440 × 960 × 4 bytes, about 5.27 MiBUnderstanding decoding cost

The last calculation assumes four-byte RGBA pixels. It is not a measured browser memory footprint and excludes other rendering overhead. Actual representations vary. Lowering encoding quality does not automatically reduce pixel count; resizing an oversized image addresses a different cost.

03

03 / Reserve the shape before arrival

If the browser cannot allocate image height during layout, the arriving image can move text. Accurate width and height attributes establish its ratio early. Responsive styling such as max-width: 100%; height: auto; still lets it shrink with its container.

A 1440-by-960 photograph displayed 600 pixels wide needs 400 pixels of height. Those attributes do not require a 1440-pixel display. A deliberately cropped container can instead reserve its own aspect-ratio; check that the crop preserves important details.

Use matching ratios across resolution candidates. Different mobile crops require corresponding space. Incorrect dimensions can still produce a correction when the image arrives. Reserving image space addresses one cause of layout shift, not every cause of CLS.

04

04 / Offer real, accurately described candidates

srcset describes existing files and their pixel widths. sizes describes the expected displayed width under different viewport conditions. Neither generates images nor sets the layout. Export these example files before using this markup.

<img
  src="workshop-960.webp"
  srcset="workshop-480.webp 480w,
          workshop-960.webp 960w,
          workshop-1440.webp 1440w"
  sizes="(max-width: 720px) calc(100vw - 32px), 680px"
  width="1440" height="960"
  alt="Scissors and colored paper beside the workshop table"
  fetchpriority="high">

This assumes 32 pixels of combined mobile margins and a 680-pixel desktop image. A two-column card needs different conditions. The browser considers display width and pixel density rather than always selecting the smallest file. Inspect the actual request at different viewport sizes and device pixel ratios.

05

05 / Protect the important first image

A large, visible photograph may become the Largest Contentful Paint element. Applying loading="lazy" can delay its request. Put a critical image in the initial HTML and avoid lazy-loading it. The example's fetchpriority="high" is a priority hint; reserve it for genuinely important resources rather than every image.

Images farther down an article can be lazy-loaded while retaining dimensions. Verify the actual LCP element with a performance recording: at another viewport size, a heading may be the largest element instead.

Smaller images cannot remove delays caused by slow server responses, late discovery, or blocked rendering. Diagnose where time is being spent before changing loading behavior.

06

06 / Make the budget a testable assumption

Try a 300 kB initial resource allowance: 110 kB for the photograph, 35 kB for each diagram, and 120 kB for everything else. At an assumed throughput of 200 kB per second, transferring that quantity alone takes 1.5 seconds.

That is neither a page-load measurement nor an LCP prediction. The division excludes connection setup, latency, scheduling, caching, decoding, and rendering. Use the budget exercise to compare choices, not to manufacture a speed score.

  1. Export candidates and inspect detail at their displayed sizes.
  2. Check selected files in the network panel, with and without cache.
  3. Resize the viewport and watch for text moving as images appear.
  4. Record test conditions and compare revisions under the same conditions.

If the allowance is exceeded, reconsider an image's presence, dimensions, or timing before endlessly reducing quality. Keep originals and export settings for future revisions.
